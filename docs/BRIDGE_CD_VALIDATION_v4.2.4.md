# v4.2.4 内部桥接与监控室 CD 联测报告

## 链路

模拟 Bear 响应 → bridge 标准化 / 校验 / 保存 → 本机 `/hunts?rank=s` → renderer 同步适配器 → 首页记录 → host binding → Chromium 内嵌监控室。

本次联测使用实际 renderer 适配器与实际监控室页面，不是直接把记录注入监控室函数。

## 通过场景

- 维护窗口 `MaintTimer=[50,80]`：监控室使用 50–80 小时。
- 正常窗口 `RespawnTimer=[84,132]`：监控室使用 84–132 小时。
- 同一击杀锚点维护状态变化：窗口更新，但不新建第二条击杀行。
- 新击杀锚点更新：击杀锚点、进闸时间、强制时间按相同偏移量更新。
- 重复快照：不重复新增记录，仍确认监控室刷新。
- 名称空格差异归一到同一怪物；不同服务器同名手动记录保留。
- 冲突记录不覆盖最后一条可信记录。
- 缺少 / 冲突维护标记、过期词库、未来击杀时间、无效可信级别和不合理超长时间窗，都无法生成已核验 CD。
- 未核验 Bear 记录在计算器和监控室显示「CD 未核验」，不展示预计进闸 / 强制时间，不允许一键回填。

## 桥接稳定性

- 只读 Bear 请求临时网络错误与 5xx 最多重试 2 次。
- 429 不重试，交由全局冷却。
- 上游写入类接口不自动重试，且匿名同步配置关闭 Bear 上游写入。
- 维护状态必须明确 true / false；未知状态不按正常 CD 调度。
- Bear 时间资源最多缓存 6 小时；过期将触发资源重新读取，读取失败则停止使用过期窗口。

## 测试结果

- 桌面端 Node 测试：26/26。
- 桥接端 Node 测试：33/33。
- Chromium E2E：通过；无页面脚本错误。
- 解压最终工程 ZIP 后再次运行 `npm run check`、`npm test` 和 Chromium E2E，均通过。

## 验证边界

Bear Timer 页面（https://tracker.beartoolkit.com/timer）由客户端 JavaScript 渲染，当前网页检索只返回启用 JavaScript 的提示，无法在本次环境读取页面实时显示值。因此本报告证明的是本机桥接 / 监控室的内部数据链和按 Bear 资源定义计算窗口的一致性，不宣称已完成线上页面逐只实时比对。Windows EXE 尚未构建或实机验证；实时轮询受 Bear 上游和网络延迟影响，不是秒级 SLA。
